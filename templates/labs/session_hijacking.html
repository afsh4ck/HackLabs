Login Target App

Inicia sesión de verdad con una cuenta de prueba cualquiera. El servidor te devolverá un SID válido en la cookie hl_hijack_sid — míralo abajo, en "Current Session", para entender cómo lo construye.

Log in for real with any test account. The server will hand you back a valid SID in the hl_hijack_sid cookie — check "Current Session" below to see how it's built.

Reuse / Inject Session ID

Este campo no comprueba ninguna contraseña: lo que escribas se guarda tal cual en tu cookie hl_hijack_sid, sustituyendo la que tuvieras. Es el equivalente a editar la cookie a mano en el navegador o con Burp. Úsalo para probar un SID que hayas deducido, forjado o adivinado sin haber iniciado sesión con esas credenciales.

This field checks no password at all: whatever you type is saved as-is into your hl_hijack_sid cookie, replacing whatever was there. It's the same as editing the cookie by hand in the browser or in Burp. Use it to try out a SID you've inferred, forged, or guessed without ever logging in with those credentials.

Easy — SID predecible

  1. Inicia sesión arriba con cualquier cuenta de prueba (por ejemplo alice / Password1) y mira la caja "Current Session": el SID que te asigna la app sigue el patrón SID-<usuario>-2024.
  2. Pulsa "Logout Session". Sin volver a autenticarte, usa el formulario "Reuse / Inject Session ID" para probar el mismo patrón sustituyendo el usuario por admin: 
    SID-admin-2024
    Alternativa por línea de comandos: 
    curl -i http://{{ target_ip }}/session-hijacking -H "Cookie: hl_hijack_sid=SID-admin-2024"
  3. El servidor solo comprueba el formato del SID y busca ese usuario en la base de datos — nunca verifica que él mismo haya emitido esa cookie. Al enviar el formulario, la página se recarga y la identidad activa pasa a ser admin.
  4. Con el rol admin activo aparece la caja verde "Flag" en esta misma página. Cópiala y valídala en la caja "Validar Flag" del lateral.

Medium — Token base64 sin firma

  1. Inicia sesión con cualquier cuenta de prueba y copia el SID que muestra "Current Session".
  2. Decodifícalo para ver su estructura real: 
    echo '<SID_COPIADO>' | base64 -d
    Verás algo como alice|user|1735000000|hacklabs-session-v1: el backend solo hace base64 decode y confía en el primer campo como usuario, sin firma ni verificación de integridad.
  3. Construye tu propio token sustituyendo usuario y rol por admin: 
    python3 -c "import base64; print(base64.urlsafe_b64encode(b'admin|admin|1735000000|hacklabs-session-v1').decode().rstrip('='))"
  4. Pega el resultado en el formulario "Reuse / Inject Session ID" (o reenvíalo con Burp Repeater) y envíalo.
  5. La app decodifica tu token, confía en el campo admin sin comprobar ninguna firma, y te asigna esa identidad — aparece la flag.

Hard — Session Fixation

  1. Visita la URL con el parámetro de fijación, eligiendo tú mismo el valor del SID: 
    http://{{ target_ip }}/session-hijacking?sid=mi-sid-elegido
    Este parámetro no debería existir en una app bien diseñada — en un pentest real se descubre probando nombres habituales (sid, session, token...) tras observar el comportamiento de las cookies.
  2. Sin tocar esa cookie, inicia sesión en el formulario de arriba con admin / password1 (la cuenta de administrador estándar de HackLabs).
    Nota: si ya completaste los labs de Forgot Password Recovery o CSRF y cambiaste la contraseña de admin, este login fallará — esos labs modifican la contraseña de forma permanente en la base de datos compartida. Usa la que fijaste en ese momento, o repite uno de esos dos labs para restablecerla a un valor que conozcas.
  3. El servidor reutiliza el mismo SID que ya tenías en vez de generar uno nuevo al autenticar — la sesión de admin queda ligada a un valor que elegiste tú de antemano, no el servidor.
  4. La página se recarga sola tras el login: la identidad activa es admin y aparece la flag.
  5. En un ataque real, el atacante enviaría ese enlace ?sid=... a la víctima (phishing) y después usaría el mismo SID en su propio navegador para heredar la sesión ya autenticada de la víctima, sin necesitar sus credenciales.

Mitigación

# Regenerar SID tras autenticación
session.regenerate()
# Firmar/validar tokens de sesión (HMAC)
# Nunca aceptar el SID desde un parámetro de URL
# Configurar cookies seguras
Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax

Easy — Predictable SID

  1. Log in above with any test account (e.g. alice / Password1) and look at the "Current Session" box: the SID the app assigns you follows the pattern SID-<username>-2024.
  2. Click "Logout Session". Without logging in again, use the "Reuse / Inject Session ID" form to try the same pattern with the username swapped for admin: 
    SID-admin-2024
    Command-line alternative: 
    curl -i http://{{ target_ip }}/session-hijacking -H "Cookie: hl_hijack_sid=SID-admin-2024"
  3. The server only checks the SID's format and looks that username up in the database — it never verifies it actually issued that cookie. Submitting the form reloads the page and the active identity becomes admin.
  4. With the admin role active, the green "Flag" box appears on this same page. Copy it and validate it in the sidebar "Validar Flag" box.

Medium — Unsigned Base64 Token

  1. Log in with any test account and copy the SID shown in "Current Session".
  2. Decode it to see its real structure: 
    echo '<COPIED_SID>' | base64 -d
    You'll see something like alice|user|1735000000|hacklabs-session-v1: the backend only base64-decodes it and trusts the first field as the username, with no signature or integrity check.
  3. Build your own token swapping username and role for admin: 
    python3 -c "import base64; print(base64.urlsafe_b64encode(b'admin|admin|1735000000|hacklabs-session-v1').decode().rstrip('='))"
  4. Paste the result into the "Reuse / Inject Session ID" form (or replay it with Burp Repeater) and submit it.
  5. The app decodes your token, trusts the admin field with no signature check, and assigns you that identity — the flag appears.

Hard — Session Fixation

  1. Visit the URL with the fixation parameter, choosing the SID value yourself: 
    http://{{ target_ip }}/session-hijacking?sid=my-chosen-sid
    A well-designed app shouldn't have this parameter — in a real pentest you'd find it by trying common names (sid, session, token...) after observing cookie behavior.
  2. Without touching that cookie, log in above with admin / password1 (HackLabs' standard admin account).
    Note: if you already completed the Forgot Password Recovery or CSRF labs and changed admin's password there, this login will fail — those labs permanently change it in the shared database. Use whatever you set it to, or redo one of those two labs to reset it to a value you know.
  3. The server reuses the SID you already had instead of generating a new one on login — the admin session ends up tied to a value you picked in advance, not the server.
  4. The page reloads itself after login: the active identity is admin and the flag appears.
  5. In a real attack, the attacker would send that ?sid=... link to the victim (phishing) and then reuse the same SID in their own browser to inherit the victim's authenticated session, without ever needing their credentials.

Mitigation

# Regenerate SID after authentication
session.regenerate()
# Sign/validate session tokens (HMAC)
# Never accept the SID from a URL parameter
# Set secure cookie attributes
Set-Cookie: sid=...; HttpOnly; Secure; SameSite=Lax
