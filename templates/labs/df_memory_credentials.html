Objetivo

Se ha volcado la memoria de otro servidor Linux — este aloja una base de datos. Recupera el historial de comandos de un administrador desde RAM antes de que lo haga otro.

Flag: — la flag está oculta en el propio fichero de evidencia; analízalo y valídala en la caja «Validar Flag» al final de esta página.

Nota sobre este volcado de memoria

Igual que en DF14, es un volcado de memoria física real de una VM Linux mínima arrancada específicamente para este laboratorio (servidor distinto, incidente distinto — no reutiliza el volcado de DF14). Incluye un proceso bash real con una sesión interactiva en curso, así que su historial de comandos vive genuinamente en memoria, exactamente como en un incidente real donde un administrador nunca llegó a cerrar sesión.

Inicio rápido

unzip memdump_dbserver01_hacklabs.zip
vol --symbol-dirs . -f memdump_dbserver01.raw.xz linux.bash
{% include 'labs/_forensic_questions.html' %}

1 · Por qué funciona

GNU bash mantiene en memoria una lista enlazada (history_list) con cada línea de comandos que el usuario ha ejecutado en la sesión interactiva, se haya volcado o no a ~/.bash_history en disco. Volatility3 sabe recorrer esa estructura directamente desde el volcado de memoria — no necesita el fichero de historial, ni que la sesión haya terminado.

2 · Descomprimir y apuntar a los símbolos

unzip memdump_dbserver01_hacklabs.zip
ls
# memdump_dbserver01.raw.xz  volatility3_symbols_debian-6.1.0-52-amd64.json.xz

Mismo mecanismo que en DF14: --symbol-dirs . apuntando a la carpeta donde has descomprimido el zip es suficiente, Volatility3 localiza el .json.xz por su banner.

3 · Recuperar el historial de bash

vol --symbol-dirs . -f memdump_dbserver01.raw.xz linux.bash

La salida reconstruye, en orden, cada comando que el administrador tecleó en su sesión:

85  bash  ...  whoami
85  bash  ...  cd /opt/backups
85  bash  ...  mysqldump -u root -pS3cr3tDBpass2024 -h 10.0.5.20 backup_db > backup.sql
85  bash  ...  ls -la
85  bash  ...  echo "backup ok - ticket ref HL{···}"

El comando mysqldump lleva la contraseña de root pegada al flag -p, en texto claro — un error clásico: cualquiera con acceso de lectura al historial de bash (o, como aquí, a un volcado de memoria) la recupera sin esfuerzo.

4 · Capturar la flag

vol --symbol-dirs . -f memdump_dbserver01.raw.xz linux.bash | grep HL
HL{···}

Mitigación

  • Nunca pasar contraseñas como argumento en la línea de comandos (-pXXXX, --password=XXXX) — usan ficheros de opciones (~/.my.cnf con permisos 600) o variables de entorno leídas por la propia herramienta, nunca visibles en ps/historial.
  • Configurar HISTIGNORE/HISTCONTROL no basta — el historial en memoria de una sesión activa sigue siendo recuperable; la única mitigación real es no teclear el secreto.
  • Usar gestores de secretos (Vault, credenciales efímeras) en vez de contraseñas estáticas para tareas administrativas recurrentes como backups.

Herramientas

Volatility 3 linux.bash

1 · Why it works

GNU bash keeps an in-memory linked list (history_list) of every command line the user has run in the interactive session, whether or not it has been flushed to ~/.bash_history on disk. Volatility3 knows how to walk that structure directly from a memory dump — it doesn't need the history file, nor does the session need to have ended.

2 · Unzip and point at the symbols

unzip memdump_dbserver01_hacklabs.zip
ls
# memdump_dbserver01.raw.xz  volatility3_symbols_debian-6.1.0-52-amd64.json.xz

Same mechanism as DF14: --symbol-dirs . pointing at the folder where you unzipped the bundle is enough — Volatility3 finds the .json.xz by its banner.

3 · Recover the bash history

vol --symbol-dirs . -f memdump_dbserver01.raw.xz linux.bash

The output reconstructs, in order, every command the admin typed in their session:

85  bash  ...  whoami
85  bash  ...  cd /opt/backups
85  bash  ...  mysqldump -u root -pS3cr3tDBpass2024 -h 10.0.5.20 backup_db > backup.sql
85  bash  ...  ls -la
85  bash  ...  echo "backup ok - ticket ref HL{···}"

The mysqldump command has root's password stuck right onto the -p flag, in plaintext — a classic mistake: anyone with read access to bash history (or, as here, to a memory dump) recovers it effortlessly.

4 · Capture the flag

vol --symbol-dirs . -f memdump_dbserver01.raw.xz linux.bash | grep HL
HL{···}

Mitigation

  • Never pass passwords as command-line arguments (-pXXXX, --password=XXXX) — use option files (~/.my.cnf with 600 permissions) or environment variables read by the tool itself, never visible in ps/history.
  • Setting HISTIGNORE/HISTCONTROL isn't enough — an active session's in-memory history is still recoverable; the only real mitigation is never typing the secret in the first place.
  • Use secrets managers (Vault, ephemeral credentials) instead of static passwords for recurring admin tasks like backups.
